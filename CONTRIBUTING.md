# Contributing & Maintaining

Maintainer notes for [cross-port-kill](README.md) (`pk` / `kp`): repository protection, releasing, development and branding. This file is not part of the npm package. See also [TESTING.md](TESTING.md) and [SECURITY.md](SECURITY.md).

## Branch protection

`main` is protected on GitHub:

- Changes arrive through a pull request, and the [CI workflow](.github/workflows/ci.yml) must pass on Linux, macOS and Windows.
- Force pushes and branch deletion are blocked, history stays linear, and review conversations must be resolved.
- Admins are not forced through these rules, so the repository owner can still push release commits (`npm version`) directly. Releases only publish when the tag points at a commit on `main`.

CI ([ci.yml](.github/workflows/ci.yml)) is skipped when a push or pull request only changes Markdown files (`**.md`). Any other file in the change, including `package.json`, `assets/` or a workflow, still runs it. Publishing is unaffected: it runs on version tags, not on file paths. Because the three test checks are required, a pull request that only edits Markdown never receives them and stays blocked for anyone who cannot bypass the rules (admins can, as above). If that ever matters, remove `paths-ignore` from the workflow.

Release tags (`v*`) are protected by a [tag ruleset](https://github.com/majidev-org/port-kill-cli/rules): only repository admins can create them, and nobody can move or delete one. Because a tag push triggers the npm publish, this keeps write-access collaborators from releasing.

Settings: *Settings → Branches* in the [repository](https://github.com/majidev-org/port-kill-cli/settings/branches). See GitHub's [branch protection docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Releasing

Publishing is automated by [.github/workflows/publish.yml](.github/workflows/publish.yml). Pushing a `vX.Y.Z` tag runs the tests on Linux, macOS and Windows, checks the tag is on `main` and matches `package.json`, and publishes to npm.

One-time setup: the workflow publishes with an npm access token stored as the `NPM_TOKEN` repository secret (*Settings → Secrets and variables → Actions*). Create a [granular access token](https://docs.npmjs.com/creating-and-viewing-access-tokens) limited to this package with read and write permission, and set a short expiry. Provenance is still signed through GitHub's OIDC token (`id-token: write`).

```bash
npm version patch          # bumps package.json and creates the vX.Y.Z tag
git push --follow-tags     # triggers the publish workflow
```

### The rename to `cross-port-kill` (2.0.0)

The package was published as `@majidev-org/port-kill-cli` up to 1.2.0. npm cannot rename a package, so `cross-port-kill` is a new package that continues at 2.0.0. A token limited to the old package cannot create a new one, so the first release needs a token that can:

1. On npmjs.com (*Access Tokens → Generate New Token → Granular Access Token*), create a token with **read and write** on **all packages** and a **1-day expiry**. Store it as the `NPM_TOKEN` repository secret.
2. Push the 2.0.0 commit to `main`, wait for CI to pass, then push the tag: `git tag v2.0.0 && git push origin v2.0.0`. The workflow publishes `cross-port-kill` with provenance.
3. Replace `NPM_TOKEN` with a token limited to `cross-port-kill` (read and write), and delete the 1-day token and the old package's token.
4. Deprecate the old package so its users are told where to go:
   ```bash
   npm deprecate @majidev-org/port-kill-cli "Renamed to cross-port-kill: npm i -g cross-port-kill (or npx cross-port-kill)"
   ```

From 2.0.1 on, releases go through the workflow as above.

## Branding

Logo and icons live in [assets/](assets/): [logo.svg](assets/logo.svg), [icon.svg](assets/icon.svg) (plus [icon-512.png](assets/icon-512.png) and [logo.png](assets/logo.png)) and [social-preview.png](assets/social-preview.png) (1280×640, for the GitHub social card). They are not part of the npm package. The SVGs are hand-drawn shapes with no font dependency; regenerate the PNGs with headless Chrome, e.g. `google-chrome --headless --window-size=512,512 --default-background-color=00000000 --screenshot=assets/icon-512.png assets/icon.svg`.

The animated terminal demo at the top of the README, [demo.svg](assets/demo.svg), is generated by [scripts/make-demo.mjs](scripts/make-demo.mjs) from the CLI's own table and color code, so it matches the real output. Run `node scripts/make-demo.mjs` after changing how the picker, `--info` or the result lines look. The picker layout is copied from `pickCheckboxes()` in [src/interactive.js](src/interactive.js), so update the script if that changes. The static screenshots (`screenshot-*.png`) are real terminal captures and need retaking by hand.
